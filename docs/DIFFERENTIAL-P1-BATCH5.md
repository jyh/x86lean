## ⛔ The family is not the batch, and that is the finding

Family 7 keys on `-------|-|flags/ctl` — *writes no flag, destination is not a
register*. That description also fits `leaveq`, `lods`, `movs`, `nop`, `pdep`,
`pext`, `retq`, `stos` and `ud2`: **string operations, BMI2 bit-manipulation, and
stack and miscellaneous forms, filed with the branches because they agree about
FLAGS.** Those 17 forms are several different templates and are not in this
batch.

⇒ 🔑 **THE ROSTER'S FAMILY KEY IS NOT A TEMPLATE KEY** (docs/DECISIONS.md D17).
The wave's headline count — "55 templates, one per family" — assumed a 1:1 map
that family 7 refutes on its own: one family, at least six templates.

## ⭐ Two roster forms that cannot be assembled

K's tree carries `jecxz_rel32.k` and `jrcxz_rel32.k`. **There is no rel32
encoding of either instruction** — `E3 cb` is rel8 only (SDM Vol. 2A, JCC).
clang refuses outright:

```
error: value of 297 is too large for field of 1 byte.
        jecxz .+300
```

K's stratification autogenerated a `rel32` variant for every branch mnemonic
without asking whether the encoding exists, and the roster — derived from K's
filenames — inherited it. **Two of the roster's 525 forms are not instructions.**
The roster selftest asserts 13 SDM facts and none of them was "every form can be
assembled"; the encoding cross-check would have caught it the moment a vector
was written, which is how it was caught.

## The new form: JRCXZ / JECXZ

The only branch whose condition is a **register**, and everything sharp about it
is the width of the register it reads. `jecxz` carries the address-size prefix
`0x67` and tests **ECX**; `jrcxz` tests all of **RCX**. One AST constructor with
an `addr32` flag, because they are one instruction with a prefix.

They disagree on exactly one shape of state: RCX non-zero with its low 32 bits
zero. The planted hard half is a model that reads all 64 bits for both — the
obvious way to write the pair once — and it produces **6 disagreements out of
19240**.

## ⭐ The claim about that, tested twice, and the second time is the point

**First version of the claim, and it was wrong.** The comment said
`0x1_00000000` is the `adversarial` constant that reaches the point. Deleting it
left the arm still catching the bug — **3 disagreements instead of 6** — because
`0x8000000000000000` is also non-zero with a zero low half. *Two* constants
reach it and either alone suffices. That is batch 2's refutation happening
again, to a comment written with the same over-confidence.

**And then the thing that had not happened before.** With *both* removed:

```
⛔ jecxz ignores the address-size prefix: ZERO disagreements
   Tests/Coverage.lean: pre_states_separate_rcx_from_ecx  — FAILS
```

`pre_states_separate_rcx_from_ecx` was written **before** the probe, against
D13's and D14's law, and it names neither constant — it asserts only that the
point is reached. ⇒ **This is the first time in this repository that a
pre-state assertion has stood in FRONT of a coverage loss rather than being
written after one was found.** D13 was written after batch 2's accident, D14
after batch 3 found the window constant; this one caught the loss on its first
real test.

The first two are P0 rows, found by reading the column rather than by any
failure — the third instance of D15's pattern in three batches. `jcc`'s is the
sharpest: **"all 16 conditions" is a count, and nothing counted it.** It is now
`vectors_cover_every_condition`, with `conditions_covered_at_both_encodings` for
the encodings and `thirty_branch_spellings` for the synonym claim, so all three
numbers in that row are theorems.
